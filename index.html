PROJECT 01

AI Dental Receptionist AI Engineering

View code

A patient-facing voice and chat receptionist that books real appointments against a real database. Patients talk or type; the AI checks genuine doctor availability and books, cancels, or reschedules — no invented availability, no mock responses.

  • Built an availability engine with slot locking and double-booking prevention, shared by the REST API, the voice widget, and the LLM tool layer through one single code path.
  • Wired real Anthropic tool-calling so the AI invokes the exact same service functions as direct API clients — voice, chat, and REST all converge on identical business logic.
  • Designed graceful degradation: with no API key configured the system returns a clear "AI unavailable" state rather than failing or faking a response.
  • Layered JWT auth, rate limiting, a NotificationService abstraction (email / SMS / WhatsApp), and a Jest suite covering the business logic.

PROJECT 02

J.A.R.V.I.S. Desktop AI

View code

A Windows desktop AI that actually operates the computer — launching apps, managing files, monitoring system health, and running gated shell commands — behind a live HUD console. Not a chatbot in a box.

  • Exposed 36 real tools across app, file, system, web, memory, and developer categories, with a drop-in skill system for adding more without touching the core.
  • Built a permission and risk engine classifying every action by permission level (safe / confirm / always-confirm) and risk (low → critical) — irreversible actions can never be silently auto-run.
  • Implemented a genuine offline rule-based intent router so the assistant is fully useful with no API key and no internet, with cloud providers swappable at runtime and nothing hard-coded.
  • Added multilingual routing (English, Urdu, Roman Urdu), a live system HUD (CPU / RAM / disk / network / battery), voice with wake word and barge-in, and an audit log of every tool call and approval.

PROJECT 03

LexOffice — Law Firm ERP Business Systems

View code

Started life as a single HTML file storing everything in browser IndexedDB — data trapped on one machine, in one browser. I re-architected it into a genuine multi-user client-server system.

  • Built an Express REST API and SQLite data layer covering clients, cases, and firm modules, with real server-side persistence replacing browser-local storage.
  • Implemented role-based permissions for Admin, Lawyer, Assistant, and Accountant, with server-verified login issuing JWT tokens.
  • Added first-run seeding so a fresh install self-populates demo data and is immediately usable — no manual setup ritual.
  • Packaged the entire stack as a cross-platform Electron desktop application (.exe / .dmg / .AppImage).

PROJECT 04

University ERP System Business Systems

View code

Three role-based portals — Student, Faculty, Admin — plus a public admissions website, all reading and writing live PostgreSQL data. Nothing in the running system is sample data.

  • Implemented attendance marking with duplicate-save prevention, results with automatic letter-grade computation, CGPA, transcripts (print / PDF), exam slips, invoices, and hostel management.
  • Built multi-step student request workflows: retest, course drop, defer term, term resume, I-grade, and final degree.
  • Secured it end to end — bcrypt hashing, fully parameterised queries, zod validation on every input, rate-limited login and write endpoints, and a Content-Security-Policy via helmet.
  • Enforced row-level ownership in SQL rather than the UI: a student can only ever read their own records, and faculty can only mark or grade students enrolled on their own courses.

03 — How I Work

Four rules I don't break

01

No fake functionality

If a button exists, it's wired to something real. Where a capability can't be delivered — no API key, no microphone — the system says so plainly and degrades gracefully instead of pretending.

02

Real over impressive

A smaller feature that genuinely works beats a bigger one that only looks like it does. Every project here runs against a real database with real data.

03

Security isn't a later step

Auth, ownership checks, input validation, and rate limiting go in with the first version — not bolted on after launch.

04

End-to-end ownership

Schema → API → UI → packaging. I don't hand off the boring parts, and I document what's real, what needs your keys, and how to run it.
